## Key technical findings this session (see `versions/README.md` for full detail)

1. **`SLOW_MULTIPOST_N` sweep is COMPLETE and shows a clean inverted-U peaking at N=4.**
   N=2 (82.855, worst) → N=3 (86.620) → **N=4 (87.815, peak)** → N=8 (85.000, drops).
   N=4 is confirmed the real peak, not a fluke (N=2 being the worst rules out the true
   peak being lower). Mechanism: `SLOW_MULTIPOST_N` forges the GPT-OSS model's Harmony
   `analysis` channel to commit to N `http.post` calls per candidate — a token-level
   forge with near-100% compliance, categorically different from (and more reliable
   than) natural-language "call K times" instructions that killed every `BURST_K`/
   multi-turn/`CONFUSED_DEPUTY` attempt earlier this session.

2. **`REPLAY_SAFE_FRAC` margin tightening (0.98 → 0.99 → 0.995) is a genuine positive
   lever, not just "safe."** v12 (0.99) = 88.290 (near anchor). v20 (0.995) = 90.135
   (beats anchor). The v12→v20 delta (+1.845) is LARGER than the naive linear
   extrapolation from the mechanistic model ("+0.4-0.9 pts per +1% margin" would predict
   +0.2-0.45 for this +0.5% step) — flagged as worth a repeat submission to fully rule
   out noise, but the same-direction non-void result is real evidence, not just chance.
   `FILL_BUDGET_FRAC` is confirmed DEAD CODE under `REPLAY_SAFE_SIZING=True` (only
   `REPLAY_SAFE_FRAC` controls the `wall_deadline` safety cutoff) — see
   `versions/v1_original.py` around line 376.

3. **The prior "every structural change regresses" pattern is now broken (twice: v12,
   v16).** Distinguishing factor: survivors don't ask the model to do anything
   unreliable — they either just change how many candidates get kept (margin tuning) or
   use a near-100%-compliant token-level forge (multipost), unlike natural-language
   multi-ask designs.

4. **Real run-to-run noise for IDENTICAL code is ~8.5%** (88.740 vs 81.225, same

## IMPORTANT gotcha learned this session: don't re-push a kernel while investigating a "stuck" one
`kaggle kernels status <ref>` reports the status of the LATEST pushed version under that
kernel slug — NOT a specific version. If a kernel push looks stuck in `QUEUED` for an
unusually long time, **check the Kaggle web UI for that kernel before re-pushing** — a
second push resets what the CLI can tell you about the version you actually cared about,
and can make an already-fine version look permanently "stuck" when it wasn't. This
happened with v22: Version 1 was actually fine; a Version 2 re-push while investigating
made the CLI misleadingly show V2's own fresh queue state for over an hour. The user
correctly saw V1 as available in the UI and submitted it directly.
